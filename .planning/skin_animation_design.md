# 桌寵動畫系統設計藍圖 (Skin Animation Design)

> 最後更新：2026-10-15（新增 §8 3D 路線評估）
> 本文件記錄「會動的角色」這個願景的架構決策與路線圖。需求原始想法見 `skinsThinks.md`。

---

## 1. 願景

單一角色 → 一隻**會走路、眨眼、做表情的完整動畫角色**，外觀**完全相同**於使用者提供的素材；
遠期可自訂動作、甚至自主行動 / 3D（3D 評估見 §8）。

---

## 2. 關鍵決策鏈（為何走到 Live2D）

| 決策點 | 結論 | 理由 |
|--------|------|------|
| 生成 vs 變形 | **變形（不生成外觀）** | 需求升級為「完全相同」，而 AI 生成永遠是重畫的新像素，無法相同 |
| 動畫機制 | **兩階段：素材 → 綁骨動畫** | 把「外觀」與「動畫」分開，各用對的工具，避免每幀又生成又要像 |
| 2D 方案 | **Live2D（Cubism）** | 業界做「會動的動漫角色」的標準；眨眼/表情/呼吸原生、即時、外觀保真 |

> **被否決的方向**：ControlNet/IP-Adapter 每幀生成（外觀無法相同、動畫會閃）；
> 純骨架變形（Animated Drawings，臉部動作弱、紙偶感）。

---

## 3. 最重要的現實（門檻）

**Live2D 需要的是「綁好骨的模型」（分層美術 + Cubism 綁定），不是一張平面圖。**
「平面圖 → 自動拆層 + 補背 + 自動綁骨成 Live2D 模型」目前是研究等級、不可靠。

→ 因此：
- 角色模型由**使用者在 Cubism Editor 綁定**（免費），或用現成分層素材 / 委託美術。
- AI 的角色從「生成角色」縮為**輔助拆層 / 補背**（研究性質，L4 才碰）。
- 使用者**已接受**此前提（2026-06-13）。

---

## 4. 架構：Live2D 如何與現有程式並存

```
PetPhysics (現有)  → 負責「視窗」在桌面的移動、重力、邊界碰撞
Live2D 模型        → 負責「角色本身」的動畫 (眨眼/呼吸/表情/走路循環)
渲染               → QLabel/QMovie (現有帧皮膚)  ‖  QOpenGLWidget + Cubism SDK (Live2D 模式)
```

- **橫向移動** = 視窗移動 (PetPhysics) + 播放 walk motion (Live2D)，兩者分工。
- **現有的擴散 AI 皮膚生成不刪**：保留為平行的「幀動畫皮膚」功能（`skin.json` 系統照用）。Live2D 是**另一種渲染模式**，非取代。

---

## 5. 路線圖

| 階段 | 目標 | 狀態 |
|------|------|------|
| **L1 引擎整合** | Live2D 範例模型在無邊框透明窗渲染，眨眼/呼吸/Pose | ✅ 完成 |
| **L2 接進桌寵** | PetPhysics 驅動、idle 動作、走路看向方向、大小縮放 | ✅ 完成 |
| **L2.4 行為細化** | 拖曳看向滑鼠、TapBody 動作、狀態→表情、Live2D 設定 UI | ⬜ 中期 |
| **L3 你的角色** | 換成使用者自己的角色模型（Cubism 綁定 / 現成素材） | ⬜ 使用者 |
| **L4 遠期研究** | AI 輔助：平面圖 → 自動拆層/補背 → 半自動綁骨 | ⬜ 之後 |

每階段單獨可測、單獨有價值。L1+L2 已用 Hiyori 驗證完成。
程式碼：`src/live2d/live2dwidget.*`；啟用：`--live2d`(桌寵) / `--live2d-test`(測試窗)。

---

## 6. 風險與注意

1. **L3 是真正門檻**：要有一個綁好的模型，主要是美術/綁定工作（非程式）。
2. **透明無邊框 + OpenGL**：Windows 上 Live2D 角色懸浮桌面、背景透明，需處理 OpenGL alpha 混合，有細節工。
3. **授權**：Cubism SDK 對個人/小團隊有免費授權（營收上限內），需註冊同意條款。
4. **L1 前置（使用者動作）**：下載 **Cubism SDK for Native (C++)** 與**範例模型**、同意授權。SDK 含 OpenGL 範例可參考。

---

## 7. L1 開始前需要的東西

- [ ] 下載 Cubism SDK for Native（含 Core 函式庫 + Framework + 範例模型，如 Hiyori/Haru）
- [ ] 放到專案某處（如 `third_party/CubismSdkForNative/`，加入 `.gitignore`，因含二進位/授權檔）
- [ ] 確認授權條款（免費 tier）
- 之後 Claude 進行：CMake 接上 Cubism Core + Framework、QOpenGLWidget 渲染、透明窗、眨眼/呼吸 idle。

## 8. 3D 路線評估（2026-10-15）

> 起因：網路上「一張圖生 3D 模型」的 AI 很多，評估能否用來做角色。結論：**生得出外殼，生不出可動的身體**。
> 桌寵要的是可驅動參數（張嘴 / 視線 / 眨眼 / 表情 / 動作），image-to-3D 一個都不給；缺口在 rig，尤其是臉部。

### 8.1 各階段現況（開源 / 免費）

| 階段 | 工具 | 狀態 |
|------|------|------|
| 單圖 → A-pose 網格 | **CharacterGen**（SIGGRAPH'24，Apache-2.0，動漫專用）／**StdGEN**（CVPR'25，權重限研究用） | ✅ |
| 網格 + 貼圖 | Hunyuan3D-2：8GB 只穩定跑形狀、貼圖慢；TRELLIS 2 官方要 24GB | ⚠️ 本機在邊緣 |
| 拓樸 | 生成網格是均勻四邊形，沒有關節 / 臉部環線 | ⚠️ 需重拓樸 |
| 身體綁骨 | **UniRig**（MIT，≥8GB）骨架 + 蒙皮一起出；公開權重非 VRoid 版，動漫效果待測 | ⚠️ |
| **臉部表情** | OmniFaceRig（155 blendshape 全自動）**程式碼未釋出** | ❌ 開源缺口 |
| 頭髮 / 布料物理 | UniRig 物理屬性尚未推出 → 先用規則依骨名配 VRM spring bone | ⚠️ |
| 組裝輸出 | Blender 無頭模式 + VRM Add-on（MIT / GPL-3.0，有 Python API） | ✅ |

多數工具 Linux 優先 → Windows 需 WSL2。

### 8.2 構想：做成獨立「外包」管線，不綁進 YaChiYo

角色生成是**一次性離線**工作，重 GPU、依賴多個研究專案，與桌寵的常駐即時渲染無關。
→ 獨立管線產出標準 **VRM** 檔，桌寵（或其他專案）只消費產物。

- **臉部缺口繞法：貼圖切換表情**。動漫 3D 常見做法，眼 / 嘴是貼圖；VRM 1.0 表情支援換貼圖，不需 blendshape。
  「閉眼版 / 張嘴版」貼圖用 **2D 局部 inpainting** 產生（只重畫眼嘴區域，其餘像素不變 → 身分一致），可沿用既有 SD 管線（`ai_server`）。
- **AI 專門處理 = 生成 → 檢查 → 重試**：每段渲染檢查圖（正 / 側 / 測試姿勢）交視覺模型判斷，不過關換種子重跑。
  宿主可做成 **Hermes skill**（Hermes 已有 terminal / file / vision / skills）。

### 8.3 接回 YaChiYo 的方式

| 選項 | 做法 | 評估 |
|------|------|------|
| **(a) 建議首選** | 3D 模型**渲染成 2D 影格** → 餵既有 `skin.json` 幀動畫 | 同一模型渲出外觀必然一致，滿足 §1「完全相同」；桌寵渲染碼零改動。限制：視角固定、嘴型格數少 |
| (b) | 獨立 VRM 渲染行程疊透明視窗 | 沿用多行程架構 |
| (c) | 桌寵內 Qt Quick 3D（支援 glTF / morph / skinning） | 最整合，但要重寫 `Live2DWidget` |

### 8.4 現實與授權

- **硬體**：RTX 4060（一般 8GB）整條在邊緣；一次性工作也可租雲端 24GB GPU 跑一次（要花錢）。
- **品質**：產出是「能動的 80% 草稿」，手指 / 臉 / 拓樸可能需 Blender 手修。
- **授權**：StdGEN 權重限研究、Hunyuan 為騰訊社群授權、UniRig 權重未載明 → 自用可，公開 / 商用須逐一確認。
- **規模**：獨立研究級專案，非週末小功能。

### 8.5 替代案：THA3 單圖動畫（2.5D）

**Talking Head Anime 3**：一張 512×512 透明背景正面立繪 → 45 維 pose（嘴含母音 / 眼 / 眉 / 頭 / 上身），**免逐角色訓練**。
程式碼 MIT、權重 **CC BY 4.0**；`separable_half` 約 40–50 fps / ~520MB VRAM。**只有上半身**（無 Walk / Fly 全身動作）。
THA4 較快但每角色要另外蒸餾，且權重為 CC BY-NC。可作獨立 Python 渲染行程，經 shared memory 送影格給 Qt。
→ 若想要「一張圖直接會動」，THA3 是最短路，驗證約一天。

### 8.6 若要動手：MVP

先驗證最不確定的兩段：
1. CharacterGen 吃使用者角色圖，產出的 A-pose 網格品質
2. UniRig 對該網格綁骨是否可用

兩段過關後剩下是已知工程（Blender 腳本、VRM 匯出）；臉部走貼圖切換；接回桌寵先走 (a)。
